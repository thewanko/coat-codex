# goal loop

## 標準形

1. 入口: `docs/state.md` と `.claude/loop/lessons.md` を読み、今回使えるルールを挙げてから着手する。過去の教訓は `.claude/loop/archive/` を Grep する（全文は読まない）。
2. design: タスクを atomic に分け、検証できる完了条件と /goal 条件を決める。
3. 実装: 下の「誰がやるか」に従う。
4. review: `review` サブエージェントに静的レビューを頼み、severity 付きの verdict を受ける。
5. 裁定: verdict を読んで採否と次の手を決める。作ったその場では裁定せず、review の結果を受けてから決める。
6. 出口: 出口ゲートを実行し、`docs/state.md` を更新、`lessons.md` に GOOD か BAD を1件追記して、追記内容を表示する。

## 誰がやるか

- セッションが直接実装する: 小〜中規模で順番に進むタスク、裁定の後の修正。
- `impl` に委譲する: 成果物ファイルが重ならない独立タスクの並列化、機械的な大量変更、長い出力を伴う作業。
- `review` は省略しない: マイルストーンの diff は必ず通す。修正の後は同じレビュアーで Round N+1 を取る。

## impl への委譲

- プロンプトに書くもの: 仕様の正の §番号、完了条件のコマンドと exit code の報告、触ってよいファイルと触ってはいけないファイル、Node 20 で実行すること、未コミットのツリーで `git stash`・`git restore`・`git checkout <path>` を使わないこと。
- 並列に委譲するときは、互いの成果物ファイル名を明示して、相手のファイルに触れないよう指示する。
- impl が Edit/Write した TS ファイルに型エラーがあると、フロントマターの Stop hook（`typecheck-gate.sh`）が1回だけ終了を差し戻す。この hook は、Bash（sed など）で書き換えたファイルと、型の変更が波及した未編集のファイルのエラーは見ない。だから裁定ではセッションが `npx tsc -b` と `npm run lint` を自分で再実行し、impl の exit code の報告をそのまま信じない（報告が不正確だったことが2回ある）。
- impl の報告を受けたら、`git status --porcelain` を指示した成果物ファイルの一覧と突き合わせ、範囲外のファイルに触れていないか確かめる。
- テストで `vi.fn` の呼び出し引数を `.mock.calls` で検証するときは、変数に関数型の注釈を付けず `vi.fn<(a: A, b: B) => R>()` の形で型を付ける。注釈を付けると Mock 型が消える。`_` 接頭辞の未使用引数はこのリポジトリの ESLint で通らない。
- 依存注入でスタブする外部 API には、実装と同じ非同期のタイミング（マクロタスクの遅延）で返すスタブを最低1ケース入れる。即時に resolve するスタブでは Dexie のトランザクションの罠を検出できない。
- impl が報告なしに終わったら（切断や上限）: `git status` と全ゲートで残骸を判定する。ほぼ完成なら欠けた部分だけセッションが補い、成果物がなければ同じプロンプトで再委譲する。中途半端な残骸の上に再委譲しない。
- impl が同じ報告を3ターン以上繰り返したら、コンテキストを失ったとみなして止める。1つのタスクで2回起きたら、そのタスクはセッションが直接実装し、BAD entry に記録する。

## review の頼み方

- 観点はマイルストーンの性質に合わせて具体的に書く: ロジック層なら境界値と実装を写しただけのテスト、データ層なら非同期・リソース管理・トランザクション、UI 層ならデザイン仕様との突き合わせと a11y。
- 修正バッチの後の Round N+1 では、「修正同士の複合作用」と「修正が持ち込んだ新しい問題」を観点に入れる。UI の状態管理（key・effect・確定のタイミング）やオーバーレイの DOM 位置（portal 化やマウント先の変更）に触れた修正なら、「修正が無効にした暗黙の前提」（z-index の序列、スタッキング文脈、イベントの伝播経路）も入れ、出口の実機検証で全操作要素のヒットテストをやり直す。
- レビュー指摘やタスク前提の事実（原因の箇所、修正案の前提、再利用する部品の能力）は、委譲や修正の前にセッションが Read・Grep・実機での再現で確かめる。食い違ったら（例: 未実装とされた対策が実装済み）、真因を確定してから design し直す。
- 危険なパターンを1か所指摘されたら、同じパターンを Grep で横断して直す。

## 出口ゲート

セッション自身が実行し、exit code を transcript に出す。

- `npx tsc -b`、`npm run lint`、`npx prettier --check apps packages "./*.{js,ts,json}"`、`npm test`（Node 20）。ビルド設定に触れたら `npm run build` も。
- UI に触れた変更は `ui-verify` skill に従って実機で確かめる。

## /goal 条件

- transcript に証跡が出る形でだけ書く: テストの exit code、ファイルの存在と全文表示、review の verdict の表示、残件数 0。
- 「production-ready」「十分に良い」のような機械判定できない表現は使わない。
- 必ず `or stop after N turns` を付ける。新しい種類のループは N=2 で試してから本番の条件にする。

## コストとコンテキスト

- ループを始める前に `/usage` で5時間枠と週次枠を確かめ、収まらないなら始めない。
- 1ループ終えたら `/clear` する（goal も消えるので、複数のループを1つの goal に詰め込まない）。
- effort は medium で始める。他人のコードのバグ・flaky テスト・スキーマ移行は high。xhigh と max は、測って効果があった作業だけに使う。

## state.md と lessons.md の書き方

- state.md の「最終更新」は最新の1件と前回の1件だけ残し、それより古い行は `docs/archive/state-history-2026.md` の「更新ログ」の先頭へ移す。各項目は3行以内にし、経緯や証跡は PR 本文へ書く。
- lessons は出口で1件追記する（GOOD でも BAD でも）。追記の前に `lessons.md` と `.claude/loop/archive/` を Grep し、同じ根本原因なら新しい entry を作らず、既存 entry の発生回数を増やす（archive にあれば `lessons.md` へ移して更新する）。
- entry は「事象・原因・一般化ルール・反映先・発生回数」を各1〜3行で書く。
- 同じ根本原因が2回目になったら、ルールとして昇格する。昇格先は、例外のない規則なら hook・ESLint・permissions、手順ならこの skill か `ui-verify`、特定ディレクトリだけの規則なら `.claude/rules/`、全タスクに共通する事実なら CLAUDE.md。
